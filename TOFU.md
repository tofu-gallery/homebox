# Tofu gallery copy

This repository is Tofu's copy of **sysadminsmedia/homebox** (licence: AGPL-3.0), listed in Tofu's app gallery as **Homebox**: a home inventory app for recording what you own, where it is kept, its receipts, warranties and maintenance.

- `main` mirrors the upstream repository and is never committed to by Tofu.
- `tofu` carries Tofu's own changes; tags named `pin/<date>` mark the versions the gallery points to. The current pin is `pin/2026-10-26`.
- A visitor who chooses this app gets a private snapshot of the pinned version in their own Tofu account. Their copy does not follow upstream updates.
- Upstream: https://github.com/sysadminsmedia/homebox at `387cd6cab0faae6d97e4819e220f88aee06e463b` (2026-10-23, v0.27.0 plus two commits). The pins up to `pin/2026-10-23.2` were made from `1fd28822634a3d5935c002d569559ef46530d4a0` (2026-10-17, v0.27.0 plus one commit); the one upstream commit since then widens the scrollbars in Chromium browsers.

## How Tofu runs it

- Framework preset `container`, root folder: the repository root. Tofu builds the root `Dockerfile` and runs the image as a service, so there is no separate install command, build command or output directory.
- The `Dockerfile` is a multi-stage build: the frontend with Node 22 and pnpm 10 (`pnpm install --frozen-lockfile`, then `pnpm build`, which runs `nuxt generate`), embedded into the Go server (`go build ./app/api/*.go`), on Alpine. The Go step uses a BuildKit cache mount (`RUN --mount=type=cache`).
- Database: PostgreSQL, the app's Tofu database, read from `DATABASE_URL`. Every start brings the schema up to date before the server listens. On PostgreSQL it does so through Tofu's locked schema step (see "Start-up when several starts run at once"), which gives an empty database the whole schema in one round trip and keeps the tables closed to the database's Data API. Without `DATABASE_URL`, Homebox falls back to SQLite under `/data`, which is lost on every restart.
- Environment: Tofu sets `PORT` and `DATABASE_URL`. The image sets `HBOX_THUMBNAIL_ENABLED=false`, `HBOX_OPTIONS_GITHUB_RELEASE_CHECK=false` and `HBOX_OPTIONS_SOURCE_URL`. Nothing has to be set by hand before the first deploy. Settings an owner may add: `HBOX_AUTH_API_KEY_PEPPER` (see below), `HBOX_OPTIONS_ALLOW_REGISTRATION=false`, and `HBOX_STORAGE_CONN_STRING` with a bucket's keys.

## What Tofu changes

- `tofu-entrypoint.sh` (new). The image now starts through this script. It does three things, then runs `/app/api` with the same arguments:
  - It sets `HBOX_WEB_PORT` to Tofu's `PORT`. Tofu sends traffic to `PORT`, and Homebox would otherwise listen on 7745. Without `PORT`, the upstream default of 7745 stays.
  - When `DATABASE_URL` is set, it splits it into the fields Homebox reads: `HBOX_DATABASE_DRIVER=postgres`, `HBOX_DATABASE_HOST`, `HBOX_DATABASE_PORT`, `HBOX_DATABASE_USERNAME`, `HBOX_DATABASE_PASSWORD`, `HBOX_DATABASE_DATABASE` and `HBOX_DATABASE_SSL_MODE`. Homebox has no setting that takes a URL. Any `HBOX_DATABASE_*` value the owner sets is kept.
  - When `HBOX_AUTH_API_KEY_PEPPER` is not set and `DATABASE_URL` is, it sets the pepper to the SHA-256 of `homebox-api-key-pepper:` followed by the whole `DATABASE_URL`, written as 64 hex characters. Homebox refuses to start without a pepper of at least 32 bytes, and Tofu does not supply one, so this lets a copy start with nothing set by hand. A pepper the owner sets always wins. See "The API key pepper" below.
- `Dockerfile`:
  - `ENTRYPOINT` is now `/bin/sh /app/tofu-entrypoint.sh`, and the script is copied into the image. The `CMD` is unchanged.
  - `HBOX_THUMBNAIL_ENABLED=false` and `HBOX_OPTIONS_GITHUB_RELEASE_CHECK=false` are now image defaults, and the owner can set either back to `true`. Thumbnails cost image processing for photos that are lost on restart anyway (see below). The release check calls GitHub every hour to show an update notice, but this copy is a fixed snapshot.
  - `HBOX_OPTIONS_SOURCE_URL=https://github.com/tofu-gallery/homebox/tree/pin/2026-10-26` is an image default: the address of this copy's exact source (see "Licence and source code").
  - `HEALTHCHECK` checks the port the server actually listens on (`PORT`, then `HBOX_WEB_PORT`, then 7745), not a fixed 7745.
- `backend/app/api/setup.go`: when `DATABASE_URL` is set, the Postgres connection adds `default_query_exec_mode=cache_describe`. Tofu's `DATABASE_URL` goes through a transaction pooler, which keeps no named prepared statements, and those are pgx's default. With this mode, every query runs on the unnamed statement.
- The schema step on PostgreSQL (from `pin/2026-10-26`; see "Start-up when several starts run at once"):
  - `backend/app/api/tofu_schema.go` (new): `tofuMigratePostgres` runs goose's migrations while one start at a time holds an advisory lock, gives an empty database the schema snapshot, and turns on row-level security.
  - `backend/app/api/setup.go`: `runMigrations`, which every server start calls, uses it on PostgreSQL. `backend/app/api/cli_reset_password.go`: the `reset-password` command uses it too. SQLite still runs `goose.Up` exactly as upstream does.
  - `backend/internal/data/migrations/tofu/postgres_snapshot.sql` (new, generated) and `backend/internal/data/migrations/tofu_snapshot.go` (new), which embeds it in the server: what the 24 postgres migrations make on an empty database, as one script. `backend/app/tools/tofusnapshot/main.go` (new) makes it. The image does not build this tool.
- A source link the copy can point at its own code, for AGPL-3.0 section 13:
  - `backend/internal/sys/config/conf.go` adds the `HBOX_OPTIONS_SOURCE_URL` setting (`options.source_url` in a config file), empty by default.
  - `backend/app/api/handlers/v1/controller.go` returns it as `sourceUrl` from `/api/v1/status`, and leaves the field out when it is empty.
  - `frontend/pages/index.vue`: the GitHub icon on the sign-in page opens that address instead of upstream's repository.
  - `frontend/layouts/default.vue`: the footer of every signed-in page shows a "GitHub Project" link to that address instead of upstream's "Version: … Build: …" release link.
  - `frontend/lib/api/types/data-contracts.ts` declares the field. That file and the API docs under `backend/app/api/static/docs` are generated upstream; the docs were not regenerated, so they do not list `sourceUrl`.
  - With `HBOX_OPTIONS_SOURCE_URL` empty, every link is exactly as upstream has it.
- `.gitlab-ci.yml` (removed in `pin/2026-10-23.2`). This is upstream's GitLab pipeline: it tests, builds and releases Homebox on upstream's GitLab, and it installs its tools by running scripts it downloads (`sh -c "$(curl …)"` and `curl … | bash`). Tofu's safety check blocks a site or app that contains such a file (five `clone-execution` findings, "GitLab CI configuration runs code downloaded from the network"), so it would stop a deploy of `pin/2026-10-23.1` or `pin/2026-10-23`. A copy never runs upstream's pipeline, and nothing else in the repository refers to the file. The file holds no licence or copyright notice. Upstream's GitHub Actions workflows under `.github/workflows/` stay, because the check has no finding on them. `.devcontainer/Dockerfile` has the same install-by-download line for the Task tool; the check does not flag it, so it stays too.
- `backend/cosign.key` (removed in `pin/2026-10-26.1`). This is upstream's Sigstore signing key, encrypted with a password only upstream holds. Nothing in the image, the app or this repository's workflows reads it. Tofu's upload refuses an archive that holds a private key, so a copy whose code is uploaded again as a ZIP would be refused. `backend/cosign.pub`, the public half, stays.

## Start-up when several starts run at once

Tofu's container hosting can start several copies of a new deployment within the same second or two, when the deployment gets its first requests. The copies share nothing but the database. Upstream's start runs `goose.Up`, which has no lock of its own and runs each migration in a transaction of its own, so on an empty database every copy created `goose_db_version` and the same tables at the same moment. On 2026-10-26 both live first deployments of `pin/2026-10-23.2` were refused: copies stopped with `relation "goose_db_version" already exists` or `duplicate key value violates unique constraint "pg_type_typname_nsp_index"` and exit code 2, and the home page answered HTTP 500. All 20 tables were also open to the database's Data API.

- **Where the lock is.** `tofuMigratePostgres` in `backend/app/api/tofu_schema.go`. `runMigrations` (`setup.go`) calls it before the server listens, and the `reset-password` command calls it before it touches the database. The lock key is the fixed number 2805111225 (crc32 of `homebox:tofu-schema`), the same in every start.
- **Which connection takes it, and why it holds through the pooler.** A transaction of its own, on the app's own connection pool, takes `pg_try_advisory_xact_lock(2805111225)` and, in the same statement, sets `idle_in_transaction_session_timeout` to 0 for that transaction only (`set_config(…, true)`). The transaction writes nothing and stays open while the schema work runs on the pool's other connections; then it is rolled back, which releases the lock. Tofu's `DATABASE_URL` is a transaction pooler (Supavisor, port 6543). It keeps one server connection with one client from `BEGIN` until the transaction ends, and lends it to other clients only between transactions. A transaction-level lock lives exactly as long as the transaction that holds it, on that server connection. A session-level lock (`pg_advisory_lock`) would stay on a server connection that the pooler goes on lending to other clients, so it is not used.
- **A start that dies while it holds the lock** drops its client connection. In Supavisor's transaction mode the server connection a client has checked out is linked to that client, and when the client goes away it closes its connection to PostgreSQL instead of returning it to the pool (`handle_event(_, {:EXIT, pid, reason}, …)` in `lib/supavisor/db_handler.ex`). PostgreSQL then rolls the transaction back, and the lock goes with it.
- **Waiting.** A start that finds the lock taken does not block inside the database. It asks again with `pg_try_advisory_xact_lock` in a short transaction, rolls back, sleeps 300 to 700 ms and checks whether the work is done, so it holds no server connection of the pooler between its questions. The holder uses two at a time: the lock's transaction and the migration that is running. After 150 s a waiting start stops with one log line, `tofu schema: another start has held the schema lock for over 2m30s; stopping this start instead of changing the schema beside it`, and exit code 1.
- **Fast path, and reading again inside the lock.** Before it asks for the lock, a start checks whether `goose_db_version` records every migration this build embeds and every table already has row-level security. If so, it skips the lock (two queries). That covers every restart, and the starts that waited during a first deployment. Inside the lock the state is read again, so a start never assumes the database is still empty.
- **An empty database** gets `backend/internal/data/migrations/tofu/postgres_snapshot.sql` in one round trip, as one simple query, which PostgreSQL runs as one transaction. It holds the 20 tables, their indexes and constraints, `goose_db_version` recording the 24 migrations, and row-level security. Then `goose.Up` runs and finds nothing to apply, or applies the migrations newer than the snapshot, and row-level security follows. goose would send every statement of every migration as a round trip of its own. The snapshot is used only when the schema holds no relation at all, `current_schema()` is `public`, every migration file it was made from is unchanged (each file's SHA-256 is on its first line), and it holds every embedded migration up to its newest. Otherwise goose makes the schema, as upstream's start does, and a database part-way through always goes through goose.
- **Duplicate objects.** A start that still meets a duplicate-object error (SQLSTATE 42P07, 42710, 42P06, 42723, 42701 or 23505) retries the whole step once. Only something that did not take the lock, such as a start of an earlier pin, could cause one.
- **Row-level security** is turned on after every `goose.Up`, in the same locked step, for every ordinary table in `current_schema()` (`public` on Tofu) that the app's role owns. That is all 20 tables, `goose_db_version` included. No policy is made: the Data API's roles (`anon`, `authenticated`) see no row and can write none, while the app's own connection owns the tables and is not limited by it. A database made by an earlier pin gets its tables closed at its first start of this one, and a table a later upstream migration adds is closed by the start that makes it.
- **What the test showed** (details under Verification). Five copies of the server, started at the same instant on an empty database through a 20 ms round trip: on `pin/2026-10-23.2`, four of the five exited with code 2 and no table had row-level security. On this pin, in every run, all five answered `/` and `/api/v1/status` within about 2 s, none exited, one applied the snapshot while the other four waited under a second, and all 20 tables had row-level security with `anon` refused. A first start alone now sends 14 statements instead of 194.
- **Keeping the snapshot current.** After merging upstream changes to `backend/internal/data/migrations/postgres`, run `go run ./app/tools/tofusnapshot '<connection string of an EMPTY scratch PostgreSQL database>'` from `backend/` with `pg_dump` on `PATH`, and commit the new file. It applies the migrations with goose, exactly as upstream's start does, and reads the schema back with `pg_dump`. A stale snapshot is never applied wrongly: a start uses it only for the migration files it still matches and goose applies the newer ones, and a changed migration file makes starts skip it.
- **One known difference.** `pg_dump` writes the two `CHECK (… IN (…))` constraints on `exports` (`exports_kind_check` and `exports_status_check`) as `= ANY (ARRAY[…])`. On a database made from the snapshot they read back in that equivalent form; they accept and refuse the same values. Everything else in the schema, and `goose_db_version`, is the same as goose makes it.

## The API key pepper

Homebox stores each API key as an HMAC keyed with `HBOX_AUTH_API_KEY_PEPPER`. Sign-in sessions use a plain hash without the pepper.

- On Tofu the pepper is derived from `DATABASE_URL` each time the container starts (above), so nothing has to be set.
- Anything that changes `DATABASE_URL` changes the pepper at the next start: a new database password, a different host, port or pooler address, other query options, or a database Tofu brings back or creates anew under a different address. After that start, every API key issued before stops working: a request with one gets `401 valid authorization token is required`. The keys still appear on the profile page and have to be deleted and created again. Sign-in sessions, passwords and the inventory itself are not affected.
- To keep API keys independent of the database address, set `HBOX_AUTH_API_KEY_PEPPER` as a hidden value on the app's Keys & settings page, at least 32 bytes, for example the output of `openssl rand -base64 48`, and keep it unchanged afterwards. Set it before creating any API key: moving from the derived pepper to your own also cancels the keys issued until then.
- The derived pepper is only as secret as `DATABASE_URL`, which Tofu keeps as a hidden value.
- Without `DATABASE_URL` (no Tofu database) and without `HBOX_AUTH_API_KEY_PEPPER`, Homebox stops at start with `auth.api_key_pepper must be set to at least 32 bytes`.

## What works differently on Tofu

- **Item photos and attachments need a storage driver.** They are written to `/data` inside the container (`HBOX_STORAGE_CONN_STRING=file:///?no_tmp_dir=true`), and that folder is lost on every restart and deploy. To keep them, point `HBOX_STORAGE_CONN_STRING` at a bucket and give the app that bucket's keys as hidden values. The image already includes the `s3://`, `gs://` and `azblob://` drivers.
- **Live refresh over a websocket is off.** A page does not update by itself when something changes in another tab or on another device; reload it to see the change. The browser console may show the page retrying `/api/v1/ws/events`.
- **Maintenance reminders need a trigger.** The running server checks once an hour. During the 08:00 hour (UTC in this image), it sends the day's scheduled maintenance through the notifiers the owner set up. If the app is asleep or restarting at that hour, nothing is sent that day. Reliable reminders need something that wakes the app on a schedule.
- **Homebox has its own login, not Tofu sign-in.** People create a Homebox account on the app's own page. Anyone who can open the address can register until the owner sets `HBOX_OPTIONS_ALLOW_REGISTRATION=false` after creating their own account, or makes the app private on Tofu.
- **The version and build numbers are blank.** The `Dockerfile` takes `VERSION`, `COMMIT` and `BUILD_TIME` as build arguments. A build given none, as in the local check below, reports all three empty, so the sign-in page's footer reads `Version: ~ Build:`.
