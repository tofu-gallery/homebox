# Tofu gallery copy

This repository is Tofu's copy of **sysadminsmedia/homebox** (licence: AGPL-3.0), listed in Tofu's app gallery as **Homebox**: a home inventory app for recording what you own, where it is kept, its receipts, warranties and maintenance.

- `main` mirrors the upstream repository and is never committed to by Tofu.
- `tofu` carries Tofu's own changes; tags named `pin/<date>` mark the versions the gallery points to. The current pin is `pin/2026-11-06`.
- A visitor who chooses this app gets a private snapshot of the pinned version in their own Tofu account. Their copy does not follow upstream updates.
- Upstream: https://github.com/sysadminsmedia/homebox at `387cd6cab0faae6d97e4819e220f88aee06e463b` (2026-10-23, v0.27.0 plus two commits). The pins up to `pin/2026-10-23.2` were made from `1fd28822634a3d5935c002d569559ef46530d4a0` (2026-10-17, v0.27.0 plus one commit); the one upstream commit since then widens the scrollbars in Chromium browsers.

## How Tofu runs it

- Framework preset `container`, root folder: the repository root. Tofu builds the root `Dockerfile` and runs the image as a service, so there is no separate install command, build command or output directory.
- The `Dockerfile` is a multi-stage build: the frontend with Node 22 and pnpm 10 (`pnpm install --frozen-lockfile`, then `pnpm build`, which runs `nuxt generate`), embedded into the Go server (`go build ./app/api/*.go`), on Alpine. The Go step uses a BuildKit cache mount (`RUN --mount=type=cache`).
- Database: PostgreSQL, the app's Tofu database, read from `DATABASE_URL`. Every start brings the schema up to date before the server listens. On PostgreSQL it does so through Tofu's locked schema step (see "Start-up when several starts run at once"), which gives an empty database the whole schema in one round trip and keeps the tables closed to the database's Data API. Without `DATABASE_URL`, Homebox falls back to SQLite under `/data`, which is lost on every restart.
- Environment: Tofu sets `PORT` and `DATABASE_URL`. The image sets `HBOX_THUMBNAIL_ENABLED=false`, `HBOX_OPTIONS_GITHUB_RELEASE_CHECK=false` and `HBOX_OPTIONS_SOURCE_URL`. Nothing has to be set by hand before the first deploy. With `DATABASE_URL` set, item photos and attachments are kept in that database by default (see "Item photos and attachments" below). Settings an owner may add: `HBOX_AUTH_API_KEY_PEPPER` (see below), `HBOX_OPTIONS_ALLOW_REGISTRATION=false`, and `HBOX_STORAGE_CONN_STRING` with a bucket's keys (which replaces the database storage).

## Start-up when several starts run at once

Tofu's container hosting can start several copies of a new deployment within the same second or two, when the deployment gets its first requests. The copies share nothing but the database. Upstream's start runs `goose.Up`, which has no lock of its own and runs each migration in a transaction of its own, so on an empty database every copy created `goose_db_version` and the same tables at the same moment. On 2026-10-26 both live first deployments of `pin/2026-10-23.2` were refused: copies stopped with `relation "goose_db_version" already exists` or `duplicate key value violates unique constraint "pg_type_typname_nsp_index"` and exit code 2, and the home page answered HTTP 500. All 20 tables were also open to the database's Data API.

- **Where the lock is.** `tofuMigratePostgres` in `backend/app/api/tofu_schema.go`. `runMigrations` (`setup.go`) calls it before the server listens, and the `reset-password` command calls it before it touches the database. The lock key is the fixed number 2805111225 (crc32 of `homebox:tofu-schema`), the same in every start.
- **Which connection takes it, and why it holds through the pooler.** A transaction of its own, on the app's own connection pool, takes `pg_try_advisory_xact_lock(2805111225)` and, in the same statement, sets `idle_in_transaction_session_timeout` to 0 for that transaction only (`set_config(…, true)`). The transaction writes nothing and stays open while the schema work runs on the pool's other connections; then it is rolled back, which releases the lock. Tofu's `DATABASE_URL` is a transaction pooler (Supavisor, port 6543). It keeps one server connection with one client from `BEGIN` until the transaction ends, and lends it to other clients only between transactions. A transaction-level lock lives exactly as long as the transaction that holds it, on that server connection. A session-level lock (`pg_advisory_lock`) would stay on a server connection that the pooler goes on lending to other clients, so it is not used.
- **A start that dies while it holds the lock** drops its client connection. In Supavisor's transaction mode the server connection a client has checked out is linked to that client, and when the client goes away it closes its connection to PostgreSQL instead of returning it to the pool (`handle_event(_, {:EXIT, pid, reason}, …)` in `lib/supavisor/db_handler.ex`). PostgreSQL then rolls the transaction back, and the lock goes with it. This holds when the start's connection really closes, as it does when its process exits. If the machine disappears and leaves the connection open, Supavisor finds out only through TCP keepalive, which can take hours, and the lock's transaction has no idle timeout; until then, waiting starts stop after 150 s with exit code 1. Only a start that disappears between taking the lock and the end of its schema step, a few round trips on an empty database, can leave the lock behind this way.
- **Waiting.** A start that finds the lock taken does not block inside the database. It asks again with `pg_try_advisory_xact_lock` in a short transaction, rolls back, sleeps 300 to 700 ms and checks whether the work is done, so it holds no server connection of the pooler between its questions. The holder uses two at a time: the lock's transaction and the migration that is running. After 150 s a waiting start stops with one log line, `tofu schema: another start has held the schema lock for over 2m30s; stopping this start instead of changing the schema beside it`, and exit code 1.
- **Fast path, and reading again inside the lock.** Before it asks for the lock, a start checks whether `goose_db_version` records every migration this build embeds and every table already has row-level security. If so, it skips the lock (two queries). That covers every restart, and the starts that waited during a first deployment. Inside the lock the state is read again, so a start never assumes the database is still empty.
- **An empty database** gets `backend/internal/data/migrations/tofu/postgres_snapshot.sql` in one round trip, as one simple query, which PostgreSQL runs as one transaction. It holds the 20 tables, their indexes and constraints, `goose_db_version` recording the 24 migrations, and row-level security. Then `goose.Up` runs and finds nothing to apply, or applies the migrations newer than the snapshot, and row-level security follows. goose would send every statement of every migration as a round trip of its own. The snapshot is used only when the schema holds no relation at all, `current_schema()` is `public`, every migration file it was made from is unchanged (each file's SHA-256 is on its first line), and it holds every embedded migration up to its newest. Otherwise goose makes the schema, as upstream's start does, and a database part-way through always goes through goose.
- **Duplicate objects.** A start that still meets a duplicate-object error (SQLSTATE 42P07, 42710, 42P06, 42723, 42701 or 23505) retries the whole step once. Something that did not take the lock, such as a start of an earlier pin, can cause one. So can a start whose lock transaction loses its own connection in the middle of the step: the start does not notice and goes on, while another start can take the lock. On the snapshot path the later snapshot then fails with a duplicate (SQLSTATE 23505) and leaves nothing behind, and its retry finds the work done; on the goose path, which only a database part-way through takes, a migration could run twice. A later pin could close this gap by asking `pg_try_advisory_xact_lock` again on the lock's own transaction before goose and before the security step: it answers true for a lock the transaction already holds and fails when the connection is gone.
- **Row-level security** is turned on after every `goose.Up`, in the same locked step, for every ordinary table in `current_schema()` (`public` on Tofu) that the app's role owns. That is all 20 tables, `goose_db_version` included. No policy is made: the Data API's roles (`anon`, `authenticated`) see no row and can write none, while the app's own connection owns the tables and is not limited by it. A database made by an earlier pin gets its tables closed at its first start of this one, and a table a later upstream migration adds is closed by the start that makes it.
- **What the test showed** (details under Verification). Five copies of the server, started at the same instant on an empty database through a 20 ms round trip: on `pin/2026-10-23.2`, four of the five exited with code 2 and no table had row-level security. On this pin, in every run, all five answered `/` and `/api/v1/status` within about 2 s, none exited, one applied the snapshot while the other four waited under a second, and all 20 tables had row-level security with `anon` refused. A first start alone now sends 14 statements instead of 194.
- **Keeping the snapshot current.** After merging upstream changes to `backend/internal/data/migrations/postgres`, run `go run ./app/tools/tofusnapshot '<connection string of an EMPTY scratch PostgreSQL database>'` from `backend/` with `pg_dump` on `PATH`, and commit the new file. It applies the migrations with goose, exactly as upstream's start does, and reads the schema back with `pg_dump`. A stale snapshot is never applied wrongly: a start uses it only for the migration files it still matches and goose applies the newer ones, and a changed migration file makes starts skip it.
- **One known difference.** `pg_dump` writes the two `CHECK (… IN (…))` constraints on `exports` (`exports_kind_check` and `exports_status_check`) as `= ANY (ARRAY[…])`. On a database made from the snapshot they read back in that equivalent form; they accept and refuse the same values. Everything else in the schema, and `goose_db_version`, is the same as goose makes it.

## The API key pepper

Homebox stores each API key as an HMAC keyed with `HBOX_AUTH_API_KEY_PEPPER`. Sign-in sessions use a plain hash without the pepper.

- On Tofu the pepper is derived from `DATABASE_URL` each time the container starts (above), so nothing has to be set.
- Anything that changes `DATABASE_URL` changes the pepper at the next start: a new database password, a different host, port or pooler address, other query options, or a database Tofu brings back or creates anew under a different address. After that start, every API key issued before stops working: a request with one gets `401 valid authorization token is required`. The keys still appear on the profile page and have to be deleted and created again. Sign-in sessions, passwords and the inventory itself are not affected.
- To keep API keys independent of the database address, set `HBOX_AUTH_API_KEY_PEPPER` as a hidden value on the app's Keys & settings page, at least 32 bytes, for example the output of `openssl rand -base64 48`, and keep it unchanged afterwards. Set it before creating any API key: moving from the derived pepper to your own also cancels the keys issued until then.
- The derived pepper is only as secret as `DATABASE_URL`, which Tofu keeps as a hidden value.
- Without `DATABASE_URL` (no Tofu database) and without `HBOX_AUTH_API_KEY_PEPPER`, Homebox stops at start with `auth.api_key_pepper must be set to at least 32 bytes`.

## Item photos and attachments

Tofu's containers scale to zero and start again on a fresh disk. Until this change, Homebox wrote item photos and attachments to a fileblob bucket at `/data` inside the container (`HBOX_STORAGE_CONN_STRING=file:///?no_tmp_dir=true`), and a restart or deploy dropped them. A copy's PostgreSQL database survives both, so this fork stores the bytes there by default. The same storage holds everything else Homebox keeps as files: thumbnails when they are turned on, collection backups (export ZIPs), which Homebox's own cleanup deletes once they are a week old (it runs at every start and then daily), and a restore's uploaded ZIP, which Homebox deletes when the restore ends, or with the week-old backups if a restart cuts the restore off. While Homebox keeps them, they take space in the database too.

- **The driver.** `backend/internal/sys/postgresblob` (new) is a `gocloud.dev/blob` driver, registered under the URL scheme `postgresblob://`. It implements the SDK's driver contract: `NewRangeReader` with offset and length; `NewTypedWriter` with the content type, `Cache-Control`, `Content-Disposition`, `Content-Encoding`, `Content-Language` and metadata, all kept with the object, and the SDK's `FailedPrecondition` result when `IfNotExist` is set and the key exists; `Attributes` with those values, the MD5 of the bytes and an ETag that changes with every write; `ListPaged` with prefix and delimiter, in UTF-8 byte order whatever the database's collation, each page going on after the last key or directory of the page before, so that a write or delete between two pages repeats, reorders or skips nothing that was there throughout; `Copy`, `Delete` and `Close`. `BeforeRead` is called once the object is found, and not for a key that is absent, as the contract asks. Three things it refuses with the SDK's documented codes instead of pretending: `SignedURL` returns `Unimplemented`, because PostgreSQL has no address a client could fetch an object from; a key that contains U+0000, which a PostgreSQL `text` value cannot hold, gets `InvalidArgument` from every operation; and so does a header value that is not UTF-8, before any byte is sent. Homebox's keys are a group id and a hex hash, and Homebox sets only a content type and an MD5, which the SDK checks itself. gocloud.dev's own conformance suite for blob drivers (`gocloud.dev/blob/drivertest`) runs against the driver as a test: every case passes or is one the suite itself skips for this driver (`TestSignedURL`, on `Unimplemented`, and `TestNonexistentBucket`, for a driver with no bucket that could be missing), except the two that write a key with U+0000 (see Verification). The driver adds no Go module: it uses the standard library, the app's existing `pgx` pool through `database/sql`, `gocloud.dev` and `github.com/google/uuid`, all of which the app already required; `go.mod` and `go.sum` are unchanged.
- **The tables.** At startup the app creates two tables with `CREATE TABLE IF NOT EXISTS`, in a transaction that takes `pg_advisory_xact_lock(2805111226)`, so several starts at once take turns (the schema step uses 2805111225). No existing table is read or changed. `tofu_blob_objects` has one row per key: `"key" text COLLATE "C" primary key`, `content_id uuid`, `content_type`, `cache_control`, `content_disposition`, `content_encoding` and `content_language` (all `text`), `metadata text` (a JSON object, or empty for none; not `jsonb`, which cannot hold U+0000), `md5 bytea`, `size bigint`, `chunk_size integer`, `created_at` and `mod_time`. `tofu_blob_chunks` holds the bytes: `"key" text COLLATE "C"`, `content_id uuid`, `seq integer` and `data bytea`, with the primary key `("key", content_id, seq)`. An object's bytes are chunks of 4 MiB, the last one shorter. Both key columns use the `C` collation, so keys sort and compare in byte order whatever the database's default collation, and a listing by prefix is a range of the primary key's index rather than a read of the whole table. In the same transaction, row-level security is turned on for each of the two tables that lacks it and that the app's role owns, the rule the schema step uses, so the database's Data API roles (`anon`, `authenticated`) read no row, as with the app's other tables. A start that finds it on already changes nothing and takes no lock on the tables, so a new instance does not make one that is serving wait.
- **Sizes.** The driver sets no limit of its own on an object. A writer holds at most one 4 MiB chunk in memory, a reader at most one piece of up to a chunk, and no `bytea` value is larger than a chunk, so neither the process's memory nor the 1 GiB ceiling of one value caps an object. The app's own limits stay as they are: 10 MB per uploaded file (`HBOX_WEB_MAX_UPLOAD_SIZE`) and 1024 MB per restore upload (`HBOX_WEB_MAX_IMPORT_SIZE`) by default. A backup grows with the collection and, for as long as Homebox keeps it, takes about as much space again as the attachments in it. The database's own size is the practical ceiling, and Tofu's database archive reaches its limit long before: it writes the whole database as one SQL file of at most 50,000,000 bytes, with every `bytea` value as hex text, two characters to a byte. Once the photos, files and backups in the two tables pass about 25 MB, less what the app's other tables take, an archive of the database stops with `artifact_too_large`. The database then cannot be archived, so it cannot be brought back from an archive either; nothing is deleted, and the database keeps running. The table editor in Tofu's dashboard reads 25 rows a page whatever their size, so a page of `tofu_blob_chunks` (up to 25 chunks of 4 MiB, shown as hex) fails as *Couldn't read this page.*, and the CSV download, which reads 500 rows at a time, cannot read that table either. `pg_dump` with the database's own connection string copies everything.
- **Writes.** A writer inserts each full chunk under a new `content_id`, all inside one transaction. At Close, in the same transaction, it points the key's row at the new content and then deletes the key's other chunks, as a statement of its own, so the chunks of a write to the same key that committed first go too. Until the commit, a reader sees the previous object, never part of the new one. A write that fails, is cancelled or is cut off by a crash rolls back and leaves nothing behind. Of two writes to the same key, the one that commits last is the object, whole, and no chunk of the other stays. An overwrite replaces the whole object: its attributes and creation time are the new write's. The writer stores the MD5 of the bytes it was given; when Homebox passes `ContentMD5`, the SDK compares the two and a mismatch rolls the write back. A zero-byte object is a row with no chunks. Holding the transaction for a whole write costs Homebox little, because it writes only from memory or from a local file: an upload is parsed before it is stored, and a backup is built in a temporary file first. Every transaction that writes, deletes or copies, and the one that creates the tables, asks for `READ COMMITTED`, which this paragraph relies on, whatever the database's default isolation: on a database or role set to `repeatable read`, the later of two writes to one key would otherwise fail with a serialization error.
- **Reads.** A reader reads the key's row when it is opened, so a request that the server answers with 304 reads no content, and the bytes from its first Read on, in pieces that never cross a chunk: the first is what that Read asks for and at least 64 KiB, and each later one at least twice the one before, up to a whole chunk. Where PostgreSQL keeps a chunk uncompressed, as it keeps a photo or any other file that is compressed already, `substring` reads only the part of the chunk a piece returns: a 64 KiB piece read 13 pages of the table's TOAST storage, not the 4 MiB chunk. After a seek, the blob SDK opens its reader again from the new offset to the end of the object, and that is what an HTTP byte range becomes, so a reader never learns how short a range is. A range of a few bytes therefore costs one 64 KiB piece, a whole download a few statements more than the object has chunks, and a download whose type Go sniffs from its first 512 bytes (a name whose extension Go does not know, such as `.heic` or `.mov`) one piece more. A request for several ranges gets the whole file with 200 (`tofu_ranges.go`): Go would serve up to 200 ranges a request, and the SDK would open the attachment once for each. A range of up to 16 MiB, which covers every upload at the default limit, reads each piece with a statement of its own and holds no connection while the client takes its bytes, and a reader holds at most one piece in memory. If a delete or overwrite of the key commits while such a range is read, its next piece fails with `FailedPrecondition`, after only bytes of the version the reader was opened on, and the download ends short. A longer range, such as a backup download or the restore reading its uploaded ZIP, reads its pieces inside one read-only `REPEATABLE READ` transaction, which holds one pooled connection until the read ends. That transaction sets `idle_in_transaction_session_timeout` to 15 minutes for itself only, so a stricter server setting does not cut a slow download off between two pieces, and a snapshot left open holds back vacuum for no longer. A delete or overwrite that commits after its first Read changes nothing it returns; one that commits before makes that Read fail with `FailedPrecondition`. No read returns bytes of two versions of an object. One Read fills the caller's buffer across pieces and chunks, and a Read after Close fails with `FailedPrecondition`. A key that is absent returns the SDK's `NotFound`; nothing panics.
- **Connections.** The driver uses the app's own pool and never more than one of its connections at a time for one operation. A write holds its connection for the whole write, and so does the read of a long range. Homebox itself writes an attachment while its own transaction for the attachment's row is open, so an upload holds two connections for a moment: one in Homebox's transaction, waiting, and one writing the bytes. Through a transaction pooler, as many uploads at the same moment as the pooler has server connections for the app could wait on each other until the pooler gives up on one, and those uploads would fail. While they wait, every other request of the app waits for a server connection too, and a transaction that sits idle meets neither `statement_timeout` nor `lock_timeout`. Homebox's pages upload one file at a time.
- **Default, and an owner's choice.** `backend/app/api/main.go` replaces only Homebox's own built-in default (`file:///./`), and only when the database driver is PostgreSQL (in any letter case, as the database setup reads it) and `HBOX_STORAGE_CONN_STRING` is unset. A value in `HBOX_STORAGE_CONN_STRING`, or one other than the default given with the command-line flag `--storage-conn-string`, always wins (Homebox reads no configuration file): an owner who already points storage at `s3://`, `gs://`, `azblob://` or a file path keeps exactly that behaviour. `tofu-entrypoint.sh` sets the old `file:///?no_tmp_dir=true` whenever the app is not on the database of a postgres `DATABASE_URL`, so a run on SQLite, or on a database configured only through `HBOX_DATABASE_*`, keeps its files under `/data` as before.
- **Existing copies.** A copy pinned to an earlier commit keeps its own image and is not affected. A copy that upgrades to this pin starts using its database. Files it had written to `/data` were already gone after its last restart or deploy, so there is nothing to migrate. Their attachment rows stay: opening one fails, as it did before the upgrade, and deleting one from the item page works, because deleting an attachment whose file is gone now deletes its row (upstream stops at the missing file and keeps the row). If an owner later sets `HBOX_STORAGE_CONN_STRING` to a bucket, the app reads only the bucket from then on: photos and files already in the two tables are not copied there, opening one fails, and deleting one deletes its row and leaves its bytes in the tables. To keep everything in a bucket, set it before attaching anything.
- **What still does not survive.** Without `DATABASE_URL` the app falls back to SQLite under `/data` and storage stays there too; both are lost on restart, as before. A copy that needs its files to survive should have a Tofu database.

## What works differently on Tofu

- **Item photos and attachments live in the app's database.** With `DATABASE_URL` set, they are kept in the PostgreSQL tables `tofu_blob_objects` and `tofu_blob_chunks`, so a restart or deploy no longer drops them; see "Item photos and attachments" above. They count towards the database's size, and so do backups for the week Homebox keeps them. Once they pass about 25 MB, Tofu can no longer archive the database, and its dashboard cannot show the table that holds the bytes (see "Sizes" above); nothing is lost, and the app keeps working. An owner who sets `HBOX_STORAGE_CONN_STRING` keeps their own bucket or file path instead.
- **Live refresh over a websocket is off.** A page does not update by itself when something changes in another tab or on another device; reload it to see the change. The browser console may show the page retrying `/api/v1/ws/events`.
- **Maintenance reminders need a trigger.** The running server checks once an hour. During the 08:00 hour (UTC in this image), it sends the day's scheduled maintenance through the notifiers the owner set up. If the app is asleep or restarting at that hour, nothing is sent that day. Reliable reminders need something that wakes the app on a schedule.
- **Homebox has its own login, not Tofu sign-in.** People create a Homebox account on the app's own page. Anyone who can open the address can register until the owner sets `HBOX_OPTIONS_ALLOW_REGISTRATION=false` after creating their own account, or makes the app private on Tofu.
- **The version and build numbers are blank.** The `Dockerfile` takes `VERSION`, `COMMIT` and `BUILD_TIME` as build arguments. A build given none, as in the local check below, reports all three empty, so the sign-in page's footer reads `Version: ~ Build:`.
